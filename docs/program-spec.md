# Aphelion 5 — Program Spec

> SNAPSHOT for programming. Master: the Program Spec doc (https://claude.ai/artifact/1SuXBNhYWUxJofhueKTKzY). Do not edit this file; rebuild it from the doc. Snapshot of 2026-11-03.

This spec tells Claude how to turn the Aphelion 5 rules into a playable single-player computer game. The rules decide what happens; this spec decides how the program is built, what the player sees, and how it is tested.

## Scope

Version 1 is a complete, solo play-through of Campaign 1 in a web browser, with every rule enforced by the program.

| In version 1 | Not in version 1 |
| --- | --- |
| Core Rules, all sections | Other campaigns (the data format must allow them later) |
| Campaign 1: all 9 missions, both alternative routes | Multiplayer, online play, accounts |
| Companies V1 and V2, including upgrades, Requisitions and Allies | A computer opponent: the enemy is the rules themselves |
| All units, Modules and Anomalies in the project files | Sound and animation beyond simple transitions |
| Heat module as an option at game setup | PC and phone apps: the same code is wrapped for them after version 1 |
| Fresh and Veteran campaigns, high scores |  |

**Technology (decided):** a web app in TypeScript, so one codebase runs in a browser now and as PC, Android and iOS apps later. The Field, tiles and animations are drawn with PixiJS, a fast 2D graphics library. Menus, panels and the question panel use React, the most common library for building interface screens; the two run side by side in one page. The rules engine is plain TypeScript with no drawing code, so it runs in tests and in every app alike. Saves live in the browser's IndexedDB, with export and import as a file. No server. After version 1, the app is wrapped for PC (Tauri or Electron) and for phones (Capacitor); layouts must work with touch, so nothing depends on hover alone.

## Sources

The program reads its game data from the project files and never hard-codes a card's numbers. When sources disagree, the order below decides, top first.

| Order | File | What it provides | How the program uses it |
| --- | --- | --- | --- |
| 1 | Component files: `unit_list_structured.txt`, `Modules.txt`, `company_vessels_structured.txt`, `Campaign1.txt`, `Anomaly list.txt` | Every unit, Module, Company, mission and Anomaly | Parsed at build time into typed data files; each effect text is hand-implemented once (see Effects) |
| 2 | `Core Rules.txt` | The rules | Implemented as engine code; the snapshot is rebuilt from the master Core Rules doc before each build stage |
| 3 | `Expansion1.txt` | The Heat module | An optional rule set, switched on at game setup |
| 4 | `claude/Test scenarios batch 1.txt` and later batches | Expected results | Turned into automated tests |
| 5 | This spec | How the program is built | Followed unless it contradicts a rule |

Component text beats the rulebook (Core Rules 11.1, rule 1), so it sits first. When Claude finds a contradiction or a gap while building, it stops, writes it down as an open question, and does not guess.

## Architecture

The rules engine is the only part that knows the rules. Everything else asks it what is legal and tells it what the player chose. Dependencies run one way: interface → engine → data.

| Part | Owns | Never does |
| --- | --- | --- |
| Data | Typed records parsed from the component files; one effect function per card | Hold game state |
| Engine | Game state, legal actions, resolving actions and effects, Alerts, Overloads, Mission End, scoring | Draw anything, read the clock, call random directly |
| Choice interface | Every question the engine asks the player, and its legal answers | Decide anything itself |
| Interface (UI) | Drawing the Field (PixiJS) and the panels and log (React); turning clicks and taps into answers | Change state except through the engine |
| Storage | Saves, Company sheets, high scores, settings | Interpret rules |
| Test harness | Loading a test's board, scripting choices, checking results | Ship in the game |

The engine is pure: given a state and an answer, it returns the next state and the next question. That makes saving, undo and testing simple, because a game is its starting seed plus its list of answers.

## Game state

One serialisable object holds the whole game; nothing about the game lives anywhere else. Each tile copy has its own id, so the same tile can be followed from deck to Field to Discard.

| Part of state | Holds | Rules |
| --- | --- | --- |
| Field | Map coordinates; per sector a stack of tiles, bottom to top | 3.1, 3.8 |
| Tile on the Field | Tile id, face up or down, facing 0–5, tokens (Damage, Shield, Bio-shield, Barrier, Alert, Wreck marker, Tick, Mortar, Feedback) | 3.2, 3.7, 6 |
| Piles | Mission deck, Energy deck, Discard, Trophy pile, Supply of tiles, Module deck, Anomaly deck | 2, 10.1 |
| Token and energy supply | Remaining counts of every limited token and each energy colour | 2, 6.7 |
| Player | Reserve energy, Modules (ready, exhausted, energy on each), Anomaly cards, Command tokens, Heat tokens | 5, Expansion1 |
| Flagship | Integrity per Bay, marked Overhaul slots | 5.2, 8.8 |
| Company sheet | Upgrade slot marks, Upgrade track points, Ally name | 7.3, 10.2 |
| Campaign | Campaign id, Fresh or Veteran, Heat on or off, mission results, chosen routes, Threat columns per mission | 7.1, 7.2, 10.3 |
| Phase | Setup, Mission Preparation, Command, Overload, Overload End, Mission End, Game End | 7–10 |
| Pending question | The choice the engine is waiting for, if any | Player choices |
| Random state | Seed and position of the random generator | Randomness |

Derived facts, such as Strength, Dark sectors or units in a row, are always computed from this state, never stored.

## Player choices

The player makes every choice, including inside enemy effects (Core Rules 11.1, rule 2). The engine therefore never picks: whenever a rule needs a choice, it stops and asks one question with a complete list of legal answers.

| Question kind | Example | Answers |
| --- | --- | --- |
| Action | Command phase or Overload | Every legal action (8.1, 9.2), plus Concede |
| Target | "Deal 2 damage to one unit" | Every unit that can be chosen; Flares and Wrecks never appear |
| Several targets | "each of two units", "up to three" | A set, with its minimum and maximum size |
| Sector | Reveal, Move, Teleport, Allied Drop | Legal sectors |
| Option | "Choose one:", ties, a Level, a row, a unit type | The listed options |
| Order | Simultaneous triggers, Fuse tokens, Alerts | Any one of the waiting items, picked one at a time |
| Amount | Extra payments, Pathfinder X, splitting damage or energy | A number or split within the limits |
| Payment | Energy colours, stored energy, Bio-shield or Shield first | Legal splits |
| Facing | Reveal and Place | 0–5 |
| Yes or no | "You may" effects, Overclock, Meltdown payment | Yes, No |

Rules for questions:

- **Auto-answer** a question with exactly one legal answer, unless the player turns that off. Never auto-answer a choice that has none: "do as much as you can" (11.1, rule 5) skips it and logs why.
- **Mandatory targets** stay mandatory (unit file E2): "skip" is offered only where the text says "you may" or "up to".
- **Hidden information** is never in an answer list. The engine offers "a Dark sector", never "the Dark sector with the Flare".
- The same question format serves the UI, the test harness and any future automatic player.

## Effects

About 270 card effects (units, Gyro Drain and Destroyed effects, Modules, Bays, upgrades, Orders) are written as short functions built from a fixed set of shared building blocks. Each building block carries the rules about it, so a card cannot forget them; each card is then a few lines.

| Building block | Carries these rules |
| --- | --- |
| Choose units / sectors / option | Chosen-unit filter (no Flares, no Wrecks), mandatory targets, "up to", different units for several targets (Modules convention 1) |
| Deal hit | One hit per instruction, Barrier first, Shields and Bio-shields before Damage, destruction at Strength 0, Bio-shield Destroyed after the effect (3.3, 6.1–6.4) |
| Destroy | Wreck for units with a Destroyed effect, Trophy pile for Omega units, top-tile check (3.4, 4.8) |
| Boost / remove damage | Shield cancels Damage, missing Shield damages the Flagship, "all" skips Flares and Wrecks (6.2) |
| Place / remove token | One Alert and one Barrier per unit, supply limits (6.5, 6.7) |
| Reveal / uncover / flip | Facing choice, Sentinel Barrier, Flare firing, Sleeper check (3.4, 4.4–4.6, 8.5) |
| Move / Swap / Teleport / Bury | Tokens travel, facing kept, top-tile check, Wrecks cannot move (glossary) |
| Rows, lines, Targeted, adjacency | Core Rules 3.8 |
| Count | Counted once when its numbered step starts; Flares and Wrecks count as units of their type (unit file E4) |
| Energy and Modules | Reserve vs. Module energy, ready-only placement, the Module being run is not ready (5.3, 5.4, 8.6) |
| Flagship damage and repair | Split across Bays, Crippled state (5.2) |
| Activate / start Overload | Alert tokens, no stacking (9.1, 11.1 rule 6) |

When a card's text cannot be built from these blocks, that is a sign of a rules gap: Claude adds it to Open questions instead of inventing a one-off rule. Every card effect gets at least one test.

The engine is a state machine over seven phases; the Command phase is the hub that every Overload returns to.

The objective and the Crippled check run only before each Command phase action (8.1), so an Overload under way always finishes first. A loss (Crippled with no Overhaul slot, or no legal action) and Concede also leave from the Command phase.

## Screen and controls

One main screen shows the Field in the centre and everything the player owns around it; the player never has to open a menu to see game state.

| Area | Shows | Player can |
| --- | --- | --- |
| Field (centre) | Pointy-top hex map; each sector's top tile, stack height, tokens as badges, arrows by facing; gaps drawn as gaps | Click a sector or unit to answer a question; hover for full card text and Strength |
| Phase bar (top) | Mission, phase (Command or Overload), objective progress, Threat columns, Command tokens, Heat | — |
| Flagship (left) | Bays with Integrity and abilities, Overhaul slots, Crippled warning | Use a Bay |
| Modules (right) | Each Module: ready or exhausted, cost, energy on it, background colour | Run a Module, return energy |
| Reserve and cards (bottom) | Energy by colour, Anomaly cards with met or not met, Orders | Issue an Order |
| Question panel | The current question in plain words, its answers, Skip where allowed | Answer; legal targets are highlighted on the Field |
| Log (collapsible) | Every action, choice and result, with rule references | Undo to a point (see Randomness) |

Other screens: game setup (Campaign, Company, Fresh or Veteran, Heat), Mission Preparation (route and Threat columns), Mission End (upgrades on the Company sheet), Game End (score and high scores).

Interaction rules:

- Only legal answers are clickable; everything else is visibly unavailable with a one-line reason on hover ("Alerts first: resolve Alerts or Overhaul").
- Face-down tiles look identical; the player sees stack heights but never contents, unless an effect shows them, and then only to that effect's end.
- During an Overload, every Alerted unit is marked and listed in the question panel in a fixed order the player can pick from.
- A rules reference (section number) is shown with every refusal and in the log, so the player and the designer can check the engine against the rulebook.

## Art

Version 1 starts with clean placeholders, and the designer's art replaces them file by file; any missing image falls back to its placeholder, so art can be added a piece at a time.

| Art | File name | Format |
| --- | --- | --- |
| Tile faces | `art/tiles/<ID>.png`, for example `art/tiles/S_12.png` | Square canvas 512 × 512 px, transparent outside a pointy-top hexagon that fills the height (flat left and right sides); drawn at facing 0, with side 1 on the left |
| Tile back | `art/tiles/back.png` | As tile faces |
| Sector plate | `art/plates/plate.png` | As tile faces |
| Module cards | `art/modules/<ID>.png`, for example `art/modules/29.png` | Portrait 750 × 1050 px |
| Anomaly cards | `art/anomalies/<ID>.png`, for example `art/anomalies/01.png` | Portrait 750 × 1050 px |
| Tokens | `art/tokens/<name>.png`: damage, shield, bio-shield, barrier, alert, wreck, tick, mortar, feedback, command, energy-yellow, energy-red, energy-blue, heat | Square 128 × 128 px, transparent |
| Company and Campaign | `art/companies/<ID>.png`, `art/campaigns/<ID>.png` | Any size, landscape |

All images are PNG (WebP also accepted), sRGB, with transparent backgrounds where noted. The program rotates tile art in 60° steps for facing, so arrows must be drawn on their printed sides. If the art is the complete printed face (Level shields, ID, arrows, text), the program shows it as is and draws tokens on top; if it is illustration only, the program adds Level, ID and arrows itself.

## Languages

English is the default; every word the player sees comes from a language file, so adding a language means adding one file and changes no rules.

- Interface text and card text live in `lang/<code>.json` (`lang/en.json` first), keyed by ID.
- The English file is generated from the component files, so card text never has two English versions.
- A card's behaviour comes from code, never from its text, so a translation cannot change how a card works.
- Layouts leave room for text up to 40% longer than English.

## Saving

The program keeps two kinds of data: the game in progress, and the things that outlive a game. Both save automatically after every answer, so closing the browser never loses work.

| Saved | Kept | Why |
| --- | --- | --- |
| Game in progress | Starting seed, setup choices and the full list of answers; a full state copy at each Mission Preparation for fast loading | Resume exactly where you stopped; replay for bug reports |
| Every Company sheet | Upgrade slot marks for each Company, including ones not played this game | Veteran campaigns, and Allied Drops use the Ally's own upgrades (7.3, 10.3) |
| High scores | Fresh and Veteran fields per Campaign, with name or date | 10.3 |
| Settings | Auto-answer, animation speed, colour-blind token shapes | Player comfort |

Rules for saves:

- **Game End clean-up** (10.3) is applied by the program: the Upgrade track, Overhaul slots and Ally name are erased; upgrade marks are kept.
- **Fresh campaign** (7.1) erases only the chosen Company's marks, never other Companies'.
- **Export and import** one file holding everything above, so the player can back up or move to another computer. Each save file carries a format version, and the program upgrades older files when it loads them.
- One game in progress at a time in version 1.

## Randomness, log and undo

All randomness comes from one seeded generator stored in the game state, so the same seed and the same answers always replay the same game.

- **Random events:** shuffling the mission deck, Energy deck, Module deck and Anomaly deck. Nothing else is random; every other uncertainty is a player choice.
- **Log:** every action, question, answer and result, in plain words with the rule section, for example "S\_12 resolves: destroys B\_01 in (0,1), Flagship takes 2 (Bay 1, Bay 2) — S\_12". The log can be exported with the save for bug reports.
- **Undo:** the player may undo any answer back to the most recent moment new hidden information appeared: a Reveal, a look at face-down tiles, a draw or a shuffle. Undo never lets a player see a tile and then take the decision back. Developer mode lifts this limit. Undo replays from the start of the mission with one answer fewer, so it can never drift from the rules.

## Developer mode

Developer mode is a switch in settings for the designer and for Claude while building; a game played with it on is marked and never records a high score.

| Tool | Does |
| --- | --- |
| Unlimited undo | Undo any answer, back to the start of the game, ignoring hidden information |
| Show hidden tiles | Shows every face-down tile and stack content on the Field |
| Load scenario | Loads a board from a test file entry (same notation as the test batches) and plays from there |
| Set seed | Starts a game from a chosen seed, to replay a reported bug |
| Edit state | Add or remove tiles, tokens, energy and Integrity by hand |
| Rule trace | Shows, for each step, which rule section and building block ran |
| Export | Saves the full state and log as a file to attach to a bug report |

## Testing and acceptance

A build stage is done only when all its tests pass; tests are written before or with the code, never after the stage is called finished.

| Test kind | What it checks | Source |
| --- | --- | --- |
| Scenario tests | The project's test files, run exactly as written: board, choices, expected result | `claude/Test scenarios batch 1.txt` and later batches |
| Card tests | Every unit, Module, Bay, upgrade and Order effect at least once, including its "do as much as you can" case | Written by Claude while implementing each card, from its text |
| Data checks | Every map is connected; Omega sectors are on their maps; copy counts add up (42 Energy Gyros, 78 Modules); every id referenced exists | Component files |
| Invariants, checked after every answer | No tile in two places; token and energy supplies never negative; a unit never holds both Shields and Damage, nor two Alerts or Barriers; Flares and Wrecks hold no tokens except their Alert (and a Wreck's marker) | Core Rules |
| Random play-throughs | Thousands of games with random legal answers on random seeds; must never crash, break an invariant or hang | Test harness |
| Replay | A saved game replays to the same state | Saving |

**Acceptance for version 1:** every test passes; a full Campaign 1 play-through is possible with each Company, with and without Heat; and the designer has played at least one full mission and agreed the program matches the rules.

When a test and the rules disagree, the rules win, and the test is fixed with a dated note.

## Build stages

Claude builds in eight stages, each ending with passing tests and a short report to the designer; the designer can play from stage 4 on.

1. **Data and geometry.** Parse every component file into typed data; build maps, neighbours, rows, lines of fire and facing (3.8). Done when the geometry tests and data checks pass.
2. **State and tokens.** The game state, tile stacks, Strength, hits, Shields, Bio-shields, Barriers, Alerts, Fuse tokens, supplies, the choice interface. Done when the token tests pass.
3. **Command phase.** Legal actions, Reveal, Mecha Attack, Scrap and abilities, Bays, Drain, Orders, Overhaul, losing, Concede.
4. **Overloads.** Starting, alerting, Overload actions, Overload End steps 1–5, Anomalies. First playable build: a text-only UI on one fixed board.
5. **Units.** Every Sentinel, Flare, Sleeper, Gyro, Omega unit and Mecha ability, in batches by type, each with card tests.
6. **Modules.** All 78, each with card tests.
7. **Campaign.** Setup, Mission Preparation, Allied Drops, Mission End, upgrades, Requisitions, scoring, saving, Fresh and Veteran, the Heat module. Done when random play-throughs of full campaigns run clean.
8. **Full interface.** The screen described above, undo, log export, settings. Done at acceptance.

Before each stage, the Core Rules snapshot is rebuilt from the master doc, and new test batches for that stage are written and agreed.
